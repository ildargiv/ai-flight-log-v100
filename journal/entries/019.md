### Неудачное  (class: харнес / конфиг)

- **Нет per-request строк движка в excerpt.** Скрипт не нашёл совпадающих строк в `lapilli-serve.log` по prompt tokens;
  `engine_log_line` = null для всех строк. Тайминги зафиксированы из SSE `timings`, это достаточно для цифр, но лог-эксцерпт
  содержит только сводку по строкам результатов.
  - как понять, что это оно: `engine_log_line: null` в `results.json`; `engine-log-excerpt.txt` без сырых строк сервера.
  - что делать вместо: подбирать паттерн под формат лога lapilli/basalt или сохранять сырой SSE/serve log рядом с прогоном.
- **Контекст ограничен 8192.** Рукав 8k не запускался: `max_context=8192`, а arm 6k уже даёт 7370 prompt tokens + 256 generation cap.
  - как понять, что это оно: `/health` возвращает `max_context: 8192`; фактический prompt 7370 на target 6144.
  - что делать вместо: отдельный прогон с поднятым/исследованным лимитом контекста lapilli, если движок/модель это поддерживает; не смешивать с этим свипом.

### Вывод (что понял сегодня; что остаётся необъяснённым)

- На V100 SXM2 lapilli-v100 + Qwen3.8-Flash-Next UD-Q4_K_XL Basalt даёт ~0.66-1.35k tok/s prefill и ~83-94 tok/s decode
  на 1k-7.4k prompt tokens, при `reused=0`, thinking off, cap 256. Decode заметно выше, чем у DeepSeek-V4.1-Flash IQ2_XXS
  в №018, но это разные модели/движки/форматы/контекстные окна — прямое сравнение некорректно.
- Prefill растёт с длиной промпта в этом окне (658 -> 1107 -> 1350 tok/s median); причина не разложена (batching/overhead/engine behavior) — наблюдение.
- Неясно: максимальный устойчивый контекст этого Basalt-пакета на lapilli-v100; поведение при >8k; влияние draft-спекуляции на decode;
  воспроизводимость после перезагрузки/другого состояния кэшей.
